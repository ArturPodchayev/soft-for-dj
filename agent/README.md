# DJ Party — локальный агент скачивания

Консольное приложение под Windows/macOS, которое DJ запускает вручную
(двойной клик) перед ивентом. Решает проблему, из-за которой автоскачивание
через Vercel не работает: Hitmo (`eu.hitmoz.com`) банит датацентровые IP —
подтверждено, один и тот же `cf-ray` colo при каждом запросе с Vercel, не
рейт-лимит и не проблема заголовков (см. `../src/lib/download/sources/index.ts`).
С обычного домашнего/venue Wi-Fi того же самого ноута DJ запрос неотличим от
рядового пользователя в браузере.

Агент:
1. Подписывается на Supabase Realtime + делает catch-up SELECT при старте —
   ловит одобренные (`status = 'approved'`) заявки, ещё не скачанные.
2. Ищет трек на Hitmo, проверяет длительность (fuzzy-match + iTunes-длительность,
   та же логика, что и в серверном пайплайне — см. "Что переиспользуется" ниже).
3. Пишет `Artist - Title.mp3` в папку Serato Watch Folder атомарно
   (`.mp3.tmp` → rename), чтобы Serato не подхватил недокачанный файл.
4. Обновляет `download_status` в БД — то же поле, что читают `/dj-view`
   (🟢/🔴) и админка.

Если трек не нашёлся / не прошёл проверку длительности — заявка помечается
`flagged_for_review = true`, `download_status = 'needs_review'`/`'failed'`,
и в `/admin` по-прежнему доступен ручной fallback (кнопки Hitmo/Sefon) —
это подстраховка на случай, если агент не запущен или упал во время сета.

## Серверный пайплайн — статус

Автотриггер (`after(() => runDownloadPipeline(...))` в
`../src/app/api/admin/songs/[id]/approve/route.ts`) **отключён** — закомментирован,
не удалён — чтобы не гоняться за одной и той же заявкой параллельно с этим
агентом (кто угодно из двух проиграл бы гонку и мог переписать `ready`
обратно в `needs_review`). Сам код (`pipeline.ts`, `googleDrive.ts`,
`cloudflare-worker/`) остался в репозитории нетронутым — просто больше
никем не вызывается.

## Что переиспользуется, а что портировано

Импортируются напрямую (не копии — один и тот же файл, две точки входа):
- `../src/lib/download/match.ts` — fuzzy-score, пороги, duration-check, фильтр
  remix/cover/live
- `../src/lib/download/filename.ts` — `"Artist - Title.mp3"`
- `../src/lib/http.ts`, `../src/lib/download/sources/{types,hitmo}.ts` — сам
  поиск/скачивание на Hitmo

Портирована (адаптирована под другое окружение) только верхнеуровневая
оркестрация в `src/pipeline.ts` — по структуре зеркальна серверной
`../src/lib/download/pipeline.ts`, но пишет файл локально вместо Google
Drive и ходит в Supabase через ограниченный клиент вместо service-role.

## Настройка (один раз, при подготовке ноута)

### 1. Применить миграцию RLS

`../supabase/migrations/0003_local_agent_rls.sql` — выполнить в Supabase
SQL Editor (или через `supabase db push`, если используете CLI). Создаёт
политики и колоночные `GRANT` для роли `authenticated`, ограниченные
`status = 'approved'` и только download-related колонками.

### 2. Создать пользователя-агента в Supabase Auth

Supabase Dashboard → Authentication → Users → Add user. Например:
`agent@internal.local` + сгенерированный пароль. Это **не** реальный
человек — просто учётка, под которой агент входит, чтобы получить роль
`authenticated` (никто больше в проекте через Supabase Auth не логинится —
админка использует свою куку, не Supabase Auth, так что это ничего не
ослабляет).

### 3. Установить зависимости и настроить `config.json`

```
cd agent
npm install
cp config.example.json config.json
```

Заполнить `config.json`:

```json
{
  "supabaseUrl": "https://xxxxx.supabase.co",
  "supabaseAnonKey": "<NEXT_PUBLIC_SUPABASE_ANON_KEY из основного .env>",
  "agentEmail": "agent@internal.local",
  "agentPassword": "<пароль из шага 2>",
  "watchFolderPath": ""
}
```

`watchFolderPath` можно оставить пустым — при первом запуске агент сам
спросит путь к папке Serato Watch Folder и сохранит его сюда же, чтобы
больше не спрашивать.

## Запуск в разработке

```
npm run dev
```

(эквивалент `npm run bundle && node dist/bundle.cjs`)

## Сборка исполняемых файлов

```
npm run build
```

Собирает `dist/DJPartyAgent-win.exe`, `dist/DJPartyAgent-mac-x64` и
`dist/DJPartyAgent-mac-arm64` (кросс-компиляция с любой ОС — зависимости
чистый JS, нативных модулей нет).

Каждому `.exe`/бинарнику нужен **свой** `config.json` рядом с ним — при
первом запуске это тот же файл, что и выше (можно скопировать
`config.example.json` и переименовать).

## Первый запуск на macOS

Собранный бинарник не подписан сертификатом Apple — Gatekeeper заблокирует
обычный двойной клик ("нельзя открыть, т.к. не удалось проверить
разработчика"). Один раз нужно: **правый клик по файлу → «Открыть»** →
подтвердить в диалоге «Открыть». Дальше запускается двойным кликом как
обычно.

## Что показывает консоль

```
[21:03:12] 🔌 Подключено к Supabase, жду заявки...
[21:03:12] ↺ Необработанных заявок при старте не найдено.
[21:07:45] 🔎 Скачиваю: Kanye West - Flashing Lights...
[21:07:51] ✅ Готово: Kanye West - Flashing Lights
[21:12:03] 🔎 Скачиваю: Неизвестный Исполнитель - Редкий Трек...
[21:12:09] ⚠️ Не найдено, отмечено для ручного поиска: Неизвестный Исполнитель - Редкий Трек (...)
```

Подробные (`[agent-pipeline-debug]`/`[hitmo-debug]`) логи включены всегда —
в отличие от серверной версии (см. `../src/lib/download/sources/hitmo.ts`),
это консоль на ноуте DJ, а не облачные логи, которые неудобно смотреть. Если
что-то пошло не так во время ивента — просто прочитай окно консоли (или
попроси прислать скриншот/скопировать текст) по звонку.

Окно консоли **не закрывается само** ни при готовом треке, ни при ошибке
поиска — агент продолжает слушать новые заявки, пока DJ сам не закроет
окно. Единственный случай, когда процесс завершается сам — фатальная
ошибка на старте (не настроен `config.json`, неверный пароль и т.п.); в
этом случае перед закрытием окно ждёт нажатия Enter, чтобы сообщение
об ошибке успели прочитать.
